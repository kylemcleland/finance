# finance

A private web app for two people to track shared expenses: monthly spending by
category, each expense allocated to **Kyle** / **Jackie** / shared, and per-category trends.

Status: data pull, classifier, CSV export, dashboard, Google sign-in, the
daily sync and Netlify hosting are in place.

## How classification works

Each transaction gets a budget category and a `share_me` percentage (how much of
it is mine; the rest is hers). Layers run cheapest first and the first one that
answers wins:

Splits use five steps: all Kyle, mostly Kyle, shared, mostly Jackie, all
Jackie (`share_me` = 100 / 75 / 50 / 25 / 0). The split belongs to the
transaction; merchants only carry defaults.

1. **Rules** (`MerchantRule` table): your own overrides, e.g. "peloton" is
   Health, all Kyle. A rule with no split ("varies", e.g. Target) fixes the
   category but asks for a decision on every purchase. Decisions in the review
   screen can be saved as a rule with one tap.
2. **Plaid category** (`personal_finance_category`) mapped onto our smaller list
   in `src/lib/categories.ts`, or a keyword table for CSV imports that have no
   Plaid category. Shared categories (groceries, rent, utilities) default to
   50/50. For personal categories the card is a hint: an account's
   `cardholder` (or Plaid's `account_owner`) says who was in the store. Coffee
   or a haircut on Jackie's card is hers; Shopping on her card is guessed hers
   but queued for review, because it could be a couch.
3. **Claude** for merchants nobody has seen before, and for every purchase at
   a "varies" merchant. It sees the amount, date and cardholder, answers in
   the five steps, and can declare a merchant "varies". Non-varying answers
   are cached per merchant. Skipped when `ANTHROPIC_API_KEY` is not set.

Anything still unresolved leans on the cardholder or splits 50/50, and is
flagged `needs_review`. The dashboard shows those as "Undecided" rather than
shared, and `/review` is where they get settled.

## Setup

Needs Node 22 and a Postgres database (local, or a free Neon one).

```bash
npm install
cp .env.example .env     # set DATABASE_URL; local only, the cloud environment uses secrets
npm run db:migrate       # applies prisma/migrations
npm run seed             # categories, three account names, starter rules
```

Secrets, never committed: `PLAID_CLIENT_ID`, `PLAID_SECRET` (or `PLAID_CLIENT_SECRET`; the Production
secret; the free Trial plan allows 10 real bank links), `PLAID_ENV=production`,
and optionally `ANTHROPIC_API_KEY`. After linking banks, also
`PLAID_ACCESS_TOKENS` so a fresh database can re-attach them.

## Getting transactions in

**From the app**: open `/banks` (linked from the dashboard), tap "Link a bank",
log into the bank in Plaid, and Plaid returns you to the app, which stores the
link. "Sync now" pulls transactions immediately; otherwise the daily sync does.
Link on the production site only: a deploy preview has its own database copy,
and each link uses one of the Trial plan's 10 permanent Item slots.

**From your real banks via Plaid, from a terminal**:

```bash
npm run plaid:link                     # prints a plaid.com URL
# open the URL, log into the bank, then:
npm run plaid:link -- --finish         # stores the link, prints PLAID_ACCESS_TOKENS
npm run plaid:sync                     # /transactions/sync, resumable via stored cursor
```

Each real bank link uses one of the Trial plan's 10 permanent Item slots, so
link each bank once. Plaid sandbox still
works for testing: set `PLAID_ENV=sandbox` and run `plaid:link -- --sandbox`.

**From a bank CSV**:

```bash
npm run import:csv -- --file samples/sample-transactions.csv
# real export: columns are detected by header; --negate if spending is negative
npm run import:csv -- --file ~/Downloads/chase.csv --account "Joint Checking" --negate
```

## Classify and export

```bash
npm run classify         # classifies new rows, writes exports/transactions.csv
npm run classify -- --all   # re-run everything except manual corrections
npm run export           # just regenerate the CSV and summary
```

The summary printed at the end shows spend by category and how much was
allocated to each person.

## Sample data

`samples/sample-transactions.csv` is synthetic (generated by `npm run sample:gen`).
Replace it with a real export from your bank, with account numbers stripped,
so the dashboard is judged against real spending.

## Dashboard and review

```bash
npm run dev          # http://localhost:3000, reads ./dev.db on every request
npm run snapshot     # exports/dashboard.html, a self-contained copy to open or publish
```

`/review` lists undecided purchases newest first. Each has five buttons (all
Kyle through all Jackie), a category picker, and an "always for this merchant"
box that writes a rule and settles the merchant's other waiting purchases.
Recent decisions can be undone from the same page.

The page is phone-first: month switcher, spend by category (tap a month),
who each expense was for, shared versus personal by month, and a per-category
table with month-over-month change, 3-month average and budget. The renderer in
`src/dashboard/render.js` is plain DOM + SVG so the same code runs in Next.js
and in the snapshot.

## Deploying on Netlify

1. The site is `kyle-jackie-finance` (https://kyle-jackie-finance.netlify.app).
   `netlify.toml` sets the build (`prisma generate && next build`) and the
   scheduled function directory. Deploy from a checkout with
   `netlify deploy --build --prod`, or connect the GitHub repo in Netlify.
2. Netlify Database provisions itself on the first deploy because
   `@netlify/database` is installed, and sets `NETLIFY_DB_URL`, which the app
   reads when `DATABASE_URL` is unset. `netlify.toml` points Netlify at
   `prisma/migrations`, so Netlify applies new Prisma migrations right before
   each production deploy is published. Never run `prisma migrate deploy`
   against the Netlify database; commit the migration and deploy.
3. Site environment variables: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`,
   `ALLOWED_EMAILS` (comma-separated) and `AUTH_SECRET` (32+ random
   characters) for sign-in; the app stays locked in production until all four
   are set. Also `PLAID_CLIENT_ID`, `PLAID_SECRET`, `PLAID_ENV=production`,
   `PLAID_ACCESS_TOKENS` after linking banks, and `ANTHROPIC_API_KEY` for the
   Claude layer.
4. Deploy. `/health` answers `{"ok":true}` to anyone without touching the
   database, so monitors and bots never wake it (Netlify bills database time).
   Signed in, it also checks the database. The `daily-sync` scheduled function
   pulls Plaid and classifies new rows at 11:00 UTC every day.

Each production deploy costs Netlify credits, so batch changes and check them
locally (`npm run build`, `npm start`) or on a free alias deploy
(`netlify deploy --build --alias staging`) before `--prod`.

## Sign-in

Google sign-in, limited to the emails in `ALLOWED_EMAILS`. In Google Cloud
Console, create an OAuth client of type "Web application" with these
authorized redirect URIs:

- `https://kyle-jackie-finance.netlify.app/auth/callback`
- `https://staging--kyle-jackie-finance.netlify.app/auth/callback`
- `http://localhost:3000/auth/callback`

The OAuth consent screen can stay in "Testing" with both emails added as test
users; the app only asks for `openid email`, so it needs no Google review.

Signing in sets a signed cookie that lasts a year, so each phone signs in once.
Removing an email from `ALLOWED_EMAILS` signs that person out on their next
visit; changing `AUTH_SECRET` signs everyone out. Locally, leaving
`GOOGLE_CLIENT_ID` unset keeps the app open for development.
